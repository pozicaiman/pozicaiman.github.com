> 姊妹篇《Cloud-Native 体系》讲的是**通用应用**在云上的运行时；本篇讲的是**智能体（Agent）**这个新物种在生产环境里"敢不敢让它跑"的那一层基础设施——身份、凭证、隔离、审计、评测与治理。ATI 不是一个具体产品，而是一类平台的抽象统称（**A**gent **T**rusted **I**nfrastructure）。
>
> 口径说明：全文以 2026 年主流 Agent 运行时（LangGraph / AutoGen / OpenAI Assistants / 自研编排）与云原生基础设施（K8s / Istio / OPA / Vault）为参考基线；不涉及任何单一厂商专有方案，机制描述以可复用能力为准。

# 第 1 章：引言 - 智能体上生产要回答的三个问题

## 1.1 为什么"能跑"不等于"敢跑"

一个 Demo 级 Agent 和一个可上线的 Agent 之间，隔着的不只是 prompt 质量，而是**一整套基础设施**：

- Demo 里 agent 拿的是你的 AK/SK，生产里它应该是**独立身份**；
- Demo 里工具随便调，生产里每一次调用都要能**授权 + 审计 + 熔断**；
- Demo 里跑挂了重跑，生产里它跑挂了要**不污染数据、不烧预算、不被追责无门**；
- Demo 里模型输出什么就用什么，生产里要能回答"这句话/这笔操作是谁做的、依据是什么、能不能撤回"。

ATI 就是把这些"生产级要求"沉淀成平台能力。

## 1.2 ATI 要回答的三份账

| 问题域 | 具体追问 | 对应能力 |
|--------|---------|---------|
| **是谁在动** | 这个 Agent / 这一次调用是谁发起的、代不代表被授权 | 身份 + 委托凭证 + 会话绑定 |
| **能动什么** | 它能访问哪些工具、数据、外部系统，边界在哪 | 策略引擎 + 工具网关 + 沙箱 |
| **动完怎么办** | 出的效果能不能追溯、能不能撤回、能不能评估 | 审计 + 回放 + 评测 + 补偿 |

> **关键认知**：ATI 不是"给 Agent 加一层安全"，而是把 Agent 当作**一类新的执行主体**去做**运行时治理**。传统应用的安全模型（进程 + 系统调用）套不到 Agent 上，因为 Agent 的行为是**语义级**的——它做的每一件事都藏在自然语言 + 工具调用序列里，安全边界必须**同时**在"符号"和"语义"两层生效。

## 1.3 全景：一次 Agent 任务穿过的那张网

```text
     用户 / 上游系统
            │
            ↓
   ┌────────────────────┐
   │  Agent 入口网关     │  ← 身份认证 + 意图识别 + 配额检查
   └─────────┬──────────┘
             ↓
   ┌────────────────────┐
   │  编排层 Orchestrator│  ← 规划 / 反思 / 子 Agent 派发
   └─────────┬──────────┘
             ↓
   ┌────────────────────┐
   │  推理层 LLM 调用    │  ← 模型路由 / Token 预算 / 内容安全
   └─────────┬──────────┘
             ↓
   ┌────────────────────┐
   │  工具网关 MCP/Function │ ← 白名单 / 参数校验 / 幂等 / 限流
   └─────────┬──────────┘
             ↓
   ┌────────────────────┐
   │  执行沙箱           │  ← MicroVM / 容器 / eBPF 系统调用过滤
   └─────────┬──────────┘
             ↓
   ┌────────────────────┐
   │  下游业务系统 / DB  │  ← 短期凭证 + 操作日志 + 回滚钩子
   └────────────────────┘

  横向贯穿：AgentID · 策略引擎(OPA) · Vault · 审计链 · Trace · 评测 · HITL
```

这张图是后文所有章节的坐标系。每一层单独看都是一个技术选型，合在一起才叫"可信基础设施"。

# 第 2 章：基础概念 - 支撑 ATI 的七个原子

## 2.1 智能体（Agent）

一个能**感知环境 → 自主规划 → 调用工具 → 观察结果 → 迭代**直到完成目标的执行体。区别于普通 LLM 调用：

| 维度 | LLM 调用 | Agent |
|------|---------|-------|
| 状态 | 无 | 有（记忆 / 计划 / 上下文） |
| 决策次数 | 单次 | 多次循环（ReAct / Plan-Act） |
| 副作用 | 只输出文本 | 通过工具改变外部世界 |
| 生命周期 | 请求级 | 会话/任务级，可跨小时/天 |

**副作用**是 ATI 存在的唯一理由——没有副作用就不需要可信基础设施。

## 2.2 Agent 身份（AgentID）

Agent 必须拥有**独立于人类用户**的可验证身份，形如 `did:agent:acme/billing-copilot/v3`。身份承载：

- 谁创建的、谁负责、哪个团队预算；
- 允许承担的角色（reader / writer / approver）；
- 生命周期状态（active / suspended / revoked）。

## 2.3 委托凭证（Delegated Credential）

Agent 代表人类用户操作时，需要一条**可验证的委托链**：
`user:alice → grants → agent:billing-copilot → acts-as → alice (scope: invoice.read)`

技术上对应 OAuth 2.0 Token Exchange（RFC 8693）或 W3C Verifiable Credential。核心约束：**短时效 + 窄作用域 + 每次操作重新兑换**。

## 2.4 工具（Tool / Function / MCP）

Agent 接触外部世界的唯一通道。工具在 ATI 中是**一等资源**，注册、发现、鉴权、限流、审计缺一不可。MCP（Model Context Protocol）当前事实上的开放规范。

## 2.5 沙箱（Sandbox）

执行代码 / 处理不可信输入时的隔离边界。按隔离强度：

```text
   弱 ←──────────────────────────────────→ 强
   容器(cgroup+ns) → gVisor → Kata MicroVM → 独立 VM → 硬件 TEE
```

选型看：**执行内容是否可预测**。让 Agent 跑用户提交的 Python 就必须 MicroVM 起步。

## 2.6 记忆（Memory）

Agent 的持久化上下文，三类：

- **短期**：对话窗口，任务级；
- **长期**：向量库 / 图数据库；
- **程序性**：工具模板、SOP、Skill 库。

记忆是**跨会话的副作用**——一旦污染会长期影响后续行为，是 ATI 里最容易被忽视的攻击面。

## 2.7 HITL（Human-in-the-Loop）

人在环：Agent 在**关键动作**前必须挂起，等人审批后才能继续。HITL 不是可选项，是 ATI 的**默认兜底**。哪些动作触发 HITL 由策略引擎决定，不由 Agent 自己决定。

# 第 3 章：工作原理 - Agent 一次任务的完整生命周期

以"Agent 处理一张客户退款工单"为例，把每一步拆开：

```text
①  入口网关收到用户请求，验证用户身份 → 生成 request_id
②  编排层根据意图路由到 billing-refund-agent → 加载 AgentID
③  策略引擎（OPA）根据 AgentID + 意图 → 计算本次允许的工具集合与阈值
④  Agent 调用 LLM 做规划 → 决定先调用 ticket.read / customer.lookup
⑤  工具网关拦截调用 → 校验 AgentID/委托凭证 → 用短期凭证换后端 API 令牌
⑥  后端系统返回数据 → 结果写入 Agent 会话记忆 + 审计 Trace
⑦  Agent 二次规划：需要发起退款 → 触发 HITL 阈值（金额 > 500）
⑧  工单挂起，推送审批人 → Agent 进入 waiting 状态（不消耗算力）
⑨  审批通过后，Agent 恢复执行 → 调用 refund.create（幂等键 request_id）
⑩  执行沙箱运行退款脚本 → 系统调用白名单过滤
⑪  调用完成 → 补偿钩子注册（若下游失败可自动 revert）
⑫  全程 Trace 落 OTel Collector → 关联 request_id / agent_id / user_id
⑬  离线评测：本次轨迹进入回归集，触发策略/提示词的下一轮迭代
```

排障、审计、复盘、合规检查，每一步都要能追到具体证据；这是 ATI 存在的意义。

# 第 4 章：技术框架 - ATI 的分层架构

## 4.1 七层视图

```text
   ┌─────────────────────────────┐
   │  ⑦ 治理与合规层              │  审计链 / 合规映射 / 报表
   ├─────────────────────────────┤
   │  ⑥ 评测与观测层              │  Trace / Eval / Regression / Drift
   ├─────────────────────────────┤
   │  ⑤ HITL 与工单层             │  审批 / 挂起 / 补偿 / SLA
   ├─────────────────────────────┤
   │  ④ 编排与推理层              │  Planner / Router / LLM Gateway
   ├─────────────────────────────┤
   │  ③ 工具与数据层              │  MCP Registry / Tool Gateway / RAG
   ├─────────────────────────────┤
   │  ② 身份与策略层              │  AgentID / Credential / OPA / Vault
   ├─────────────────────────────┤
   │  ① 运行时层                  │  沙箱 / K8s / Serverless / eBPF
   └─────────────────────────────┘
```

每层都可以独立选型：

| 层 | 主流开源/标准 |
|----|--------------|
| 运行时 | K8s Job / Knative / Firecracker / gVisor / Kata |
| 身份策略 | SPIFFE / OIDC / OAuth2 Token Exchange / OPA-Kyverno / Vault |
| 工具数据 | MCP / OpenAPI Function / LangChain Tools / LlamaIndex |
| 编排推理 | LangGraph / AutoGen / CrewAI / 自研 |
| HITL | 工单系统 / Temporal / 自研工作流 |
| 评测观测 | OpenTelemetry + LangSmith / Phoenix / Braintrust / OpenRL |
| 治理合规 | 审计日志不可篡改存储（哈希链 / Merkle） + 合规映射 |

## 4.2 与云原生栈的映射

ATI **不是**新造一套基础设施，它是**云原生栈 + 一层语义**：

| 云原生组件 | ATI 对应 |
|-----------|---------|
| Kubernetes Deployment | Agent 实例化 + 生命周期 |
| Service Mesh | 工具调用治理（重试/熔断/追踪） |
| Ingress / Gateway API | Agent 入口网关 |
| Prometheus / OTel | Trace + Token 消耗 + 决策延迟 |
| OPA / Kyverno | Agent 行为策略（可做什么工具/参数范围） |
| Vault | Agent 短期凭证 + 委托链 |
| GitOps | Agent 提示词/工具/Skill 版本化 |

这个映射意味着：**已有云原生团队可以直接演进**，不必推倒重来。

# 第 5 章：设计思想 - ATI 的六条底层原则

## 5.1 零信任：默认拒绝

Agent 每一次工具调用都独立鉴权，不复用"上一次已经通过"。会话级"授权"要显式声明作用域（哪些工具、哪些参数、多少次、多长 TTL）。

## 5.2 最小权限：Per-Task Just-in-Time

Agent 身份 ≠ Agent 权限。同一 Agent 在不同任务上应该被临时授予**不同的**能力。权限由策略引擎按 (agent_id, task_context, tenant_policy) 三元组现算。

## 5.3 可验证：每一步都能追溯

任何一次操作，事后要能回答四问：**谁做的、基于什么信息、按什么规则、影响是什么**。这四问对应审计链的四个字段：actor / context / policy / effect。

## 5.4 可撤回：为副作用配补偿

工具设计阶段就要成对提供 `do` 和 `undo`。Agent 层不感知补偿，由运行时在事务边界上自动触发。做不到补偿的动作（如发短信）应在 HITL 阈值上更保守。

## 5.5 可回放：Trace 是资产

完整回放一次 Agent 执行，等于免费的调试 + 免费的评测 + 免费的合规证据。Trace 结构要能重放推理链、工具调用、上下文快照三件事。

## 5.6 分层收敛：让 Agent 之间也能级联治理

多 Agent 协作时，被调方 Agent 拿到的是**"委托链 + 收敛后权限"**——委托只能收窄，不能扩展。子 Agent 永远拿不到比父 Agent 更宽的作用域。

# 第 6 章：核心模块 - 一个可用的 ATI 平台必须有什么

## 6.1 AgentID 服务

- 签发 / 轮换 / 吊销 Agent 身份；
- 与人类用户/组织的**归属关系**；
- 与 SPIRE / OIDC Provider 集成，输出可验证令牌。

## 6.2 凭证与委托链服务

- OAuth 2.0 Token Exchange + 短 TTL；
- 每次外部调用现换、不缓存；
- 委托链可验证（用户 → 主 Agent → 子 Agent → 工具）。

## 6.3 策略引擎

- 输入：`(agent_id, tool_name, args, tenant, task_context)`；
- 输出：allow / deny / require_approval / rate_limit / arg_rewrite；
- 规则用 OPA Rego / 代码策略；变更走 GitOps。

## 6.4 工具网关（MCP Gateway）

- 工具注册中心 + 版本管理；
- 参数 schema 校验 + 语义校验（防"参数合法但意图违规"）；
- 幂等键、重试、熔断、限流；
- 每一次调用写审计。

## 6.5 执行沙箱

- 代码执行 / 浏览器 / 文件系统三类沙箱；
- 出站网络白名单；
- 系统调用过滤（seccomp / eBPF）；
- 冷启动 200ms 以内。

## 6.6 记忆治理

- 读写分离（Agent 只能读**自己 + 授权共享**的记忆）；
- 记忆条带来源标注（哪次会话、哪份文档）；
- 敏感记忆的静态加密 + 定期过期；
- 投毒检测（写入前扫描、批量异常告警）。

## 6.7 LLM 网关

- 模型路由（成本/延迟/合规约束）；
- Token 预算（per-agent / per-tenant / per-task）；
- 内容安全双向检查；
- 幻觉与越权的语义兜底（可选 guard model）。

## 6.8 观测与评测

- 完整 Trace：Agent 决策 + LLM Prompt + 工具调用 + 结果；
- 关键指标：任务成功率 / 平均步数 / HITL 触发率 / 越权拦截 / 成本；
- 离线评测集 + 回归流水线；
- 灰度发布：新提示词/新工具用流量比例逐步放开。

## 6.9 审计与合规

- 审计日志哈希链 + 不可篡改存储；
- 敏感动作强留痕（谁批准、批准时看到什么）；
- 合规映射（GDPR 数据主体请求 / 等保 / SOC2）；
- 定期导出与抽查工具。

# 第 7 章：应用场景

## 7.1 高适配场景

| 场景 | 为什么必须 ATI |
|------|---------------|
| **金融/支付的自动化客服** | 有真实资金副作用，合规强制审计 |
| **企业 IT 运维助手（AIOps）** | Agent 拥有 kubectl/root 级操作，越权代价大 |
| **医疗辅助问诊** | PHI 数据 + 决策留痕 |
| **法务合同审阅 + 起草** | 敏感文档 + 委托链 |
| **供应链 / 采购智能体** | 涉及下单、付款、审批 |
| **代码助手 CI/CD 集成** | 会直接改代码库、发流水线 |
| **多 Agent 协作工作流** | 委托链 + 权限收敛的必要性最强 |

## 7.2 谨慎评估的场景

- **纯聊天/问答类 Copilot**：无副作用，可以只做基础 LLM 网关。
- **离线/研究 Agent**：不需要生产级 SLA 与审计。
- **完全人监督的探索性 Agent**：HITL 覆盖每一次操作，可暂时不建独立身份体系。

## 7.3 常见反模式

| 反模式 | 危害 |
|--------|------|
| Agent 用人类账号凭证直接跑 | 审计断链、权限失控、密码泄露 |
| 工具 API 直接暴露给 Agent（无网关） | 无法限流 / 无法参数改写 / 无 Trace |
| 提示词写"不要执行危险操作"当作策略 | 提示注入即破防 |
| 记忆全租户共享一个向量库 | 数据串门、合规事故 |
| HITL 审批只看摘要不看上下文 | 人被 Agent 反向操控 |
| 只有 Trace 没有 Eval | 出问题只能事后翻日志，无法主动收敛 |

# 第 8 章：性能参数 - 各层的量级参考

以下为 2026 年主流部署的经验区间，用于容量估算，非 SLA。

| 层 | 关键指标 | 典型量级 |
|----|---------|---------|
| 入口网关 | 认证 + 路由延迟 P99 | 10~50ms |
| 策略引擎 | 单次 allow/deny P99 | 1~5ms（本地 sidecar）；10~30ms（集中部署） |
| 凭证兑换 | Token Exchange 延迟 | 20~80ms；短 TTL 下 QPS 高时是主要瓶颈 |
| LLM 网关 | 首 Token 时间 TTFT | 依赖后端，本地部署 200~500ms，云 API 500ms~2s |
| 工具网关 | 单次调用额外开销 P99 | 5~20ms |
| 执行沙箱 | 冷启动 | 容器 200ms；gVisor 500ms；Kata 1s；Firecracker 150ms |
| 记忆检索 | 向量 top-k P99 | 10~50ms（十亿级需要专门索引） |
| 审计落盘 | 关键事件写入 | 亚秒；用异步批写下的极端 P99 需控制在 5s 内 |
| HITL 挂起 | 状态保存与恢复 | 秒级；长挂起依赖 Temporal 类持久化工作流 |
| 端到端 | 一个 5 步 Agent 任务额外基础设施开销 | 100~300ms（相对 LLM 推理本身可以忽略） |

## 8.1 成本口径

一个稳定运行的 Agent 平台，**基础设施开销**（不含模型 API）通常是模型成本的 **15~35%**。要提前预算：

- 沙箱：按并发峰值预留；空闲回收要激进；
- 观测：Trace 采样与保留周期是最大变量；
- 策略引擎：集中式部署时高 QPS 需要水平扩容；
- 记忆：向量库 + 长期存储 + 快照，是慢但确定的开销。

## 8.2 关键 SLO 建议

- **越权拦截召回率 ≥ 99%**：一次漏检就是合规事故；
- **审计链完整性 100%**：宁可拒服务，不可写坏审计；
- **任务级 Trace 完整率 ≥ 99.9%**；
- **HITL 挂起最大恢复时间 ≤ 5min**；
- **Agent 冷启动 P99 ≤ 2s**（交互式场景）。

# 第 9 章：问题与缺陷 - ATI 不是万能

## 9.1 提示注入与语义越权

只要 Agent 会读"不可信文本"（网页 / 邮件 / 用户上传文档），就有注入风险。当前缓解手段：

- 输入隔离：用特殊 token / JSON 结构分离不可信内容与指令；
- 双向内容安全模型：进 LLM 前扫一次，出 LLM 后再扫一次；
- **工具白名单收窄**：把"能被注入诱发的动作"（如任意 URL fetch）从工具集里砍掉；
- 高危动作二次校验（策略引擎独立于 LLM 判断）。

没有一种单点方案能防住提示注入，只有**分层降低爆炸半径**。

## 9.2 委托链的用户体验代价

每步都换短期凭证、每次都 HITL，会让 Agent 慢到不能用。需要在**风险 × 时延**上做权衡：低风险动作用批量授权 + 事后审计，高风险动作严格链。

## 9.3 记忆污染的隐蔽性

一次攻击写入的错误记忆，会在**几个月内**持续误导 Agent。防御难点：

- 记忆来源不可信；
- 记忆与"事实"难以区分；
- 清理一条记忆要考虑下游所有派生记忆。

务实做法：**记忆分层 + 来源标注 + 定期人审 + 高风险记忆走"候选 → 采纳"两阶段**。

## 9.4 评测的天花板

Agent 任务的正确性极难自动判定。LLM-as-Judge 有偏，规则判定覆盖不全，人工评测又贵。这是当前整个行业共同的短板。可行的收敛路径：

- 用**可验证子目标**替代端到端打分（工具调用是否合法、参数是否在范围）；
- 建立回归集，任何改动过一遍历史 case；
- 在线 A/B 抽样人评。

## 9.5 供应链

Agent 依赖的模型、工具、Skill、MCP Server、检索数据全是外部组件。任何一个被投毒都会跨边界放大。要沿用云原生的 SLSA/SBOM 思路：模型也签、MCP 也签、Skill 也签、依赖可枚举。

## 9.6 组织与责任

Agent 犯的错算谁的——写提示词的？批准上线的？还是运行时没拦住的？如果权责不清，平台会被业务绕过。**ATI 的落地从来都是"组织问题优先于技术问题"**。

# 第 10 章：解决方案与最佳实践

## 10.1 渐进式落地路径

```text
阶段1：入口网关 + 基础身份 + 全量 Trace    （看得见）
阶段2：工具网关注册 + 参数校验 + 策略引擎  （管得住）
阶段3：委托链 + 短期凭证 + HITL 挂起       （不越权）
阶段4：沙箱 + 记忆治理 + 供应链签名        （不污染）
阶段5：Eval 平台 + 回归集 + 灰度发布       （可迭代）
阶段6：审计链上链 / 合规映射 / 跨租户隔离  （可追责）
```

任何一次跳过都会在未来某个具体事故里被追缴回来。

## 10.2 设计层建议

- **工具粒度小一点**：一个工具一件事，参数明确，方便策略与幂等；
- **副作用显式声明**：工具元数据里写清 read / write / external / irreversible；
- **上下文压缩**：Trace 与记忆要能摘要，避免长期成本失控；
- **失败即挂起**：Agent 不确定时优先挂起而不是猜测。

## 10.3 安全层建议

- 默认出站拒绝 + 域名白名单；
- 密钥永不下发到 Agent 侧（只在工具网关注入）；
- eBPF 层拦截异常 syscall；
- Agent 身份与人类身份**同一目录不同命名空间**，方便审计统一视图。

## 10.4 观测层建议

- 三级关联：`user_id ↔ agent_id ↔ request_id`；
- 每个 LLM 调用记 prompt 摘要（不含敏感原文）+ token 用量；
- 每个工具调用记 (tool_name, args_hash, result_summary, latency, cost)；
- 提供**时间轴回放 UI**，让排查一次 Agent 事故像看录像。

## 10.5 治理层建议

- Agent 上线走"注册 → 评审 → 灰度 → 全量 → 定期复评"；
- 每季度做一次 Agent 权限大扫除（僵尸工具、过期委托、宽策略）；
- 建立"越权事件"库，任何一次真实拦截都进回归集；
- 明确 Agent 决策可申诉路径（人可以随时否决、追溯）。

# 第 11 章：未来趋势（2026 视角）

## 11.1 MCP 事实标准 + Agent 目录

跨厂商 Agent 相互发现、相互授权会成为公共基础设施。类似 DNS 的角色：一个可验证的 Agent 目录（Agent Directory）承载身份、能力、信誉。

## 11.2 硬件级可信执行

TEE（Intel TDX / ARM CCA / NVIDIA Confidential Computing）从数据库走向 Agent 推理，为高敏行业提供"平台方也看不到数据"的选项。

## 11.3 语义防火墙

专门做"意图审计"的小模型/规则引擎：独立于业务 LLM，判断"这一步是不是像被劫持了"。作为 LLM 之外的第二双眼睛。

## 11.4 可携带身份

用户在不同厂商 Agent 之间漫游时携带统一凭证与授权偏好，类似浏览器隐私模式。W3C VC / DIDs 生态会先落在这块。

## 11.5 平台工程向 Agent 工程演进

云原生讲 Platform Engineering，ATI 之后会出现 **Agent Engineering**：负责把工具/策略/评测/审计做成" paved road"，让业务方一键接入。

## 11.6 合规显性化

国内《生成式人工智能服务管理办法》、欧盟 AI Act、SOC2 for AI——ATI 会像 K8s 之于 DevOps 一样，成为**合规证据的天然载体**。审计链 + Trace + Eval 是合规谈判的三件套。
