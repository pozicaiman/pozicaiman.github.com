# 第 2 章：Platform Engineering

平台工程、IDP、平台产品化
单机时代：一台服务器包含一个应用（如 Web 应用、数据库、文件服务器等）整个系统支撑无数互联网用户访问。
多机时代：Nginx拆分前后端，数据库拆分读写，文件服务器拆分读写等。
虚拟机时代：每个应用都有自己的虚拟机，虚拟机之间通过网络通信。
容器时代：每个应用都有自己的容器，容器之间通过网络通信。
容器编排时代：Kubernetes集逐渐兼容算力、存储、网络等资源。进而实现了容器的自动部署、自动扩展、自动恢复等功能。
平台产品化：企业开始关注平台产品化，如容器化平台、微服务架构等。

# 第 4 章：Autonomous IT & AI SRE

AIOps、Agent Ops、Agentic Ops、Embodied Ops、自主运维

一条主线：作用域从数字世界走向物理世界，自主度从“辅助人”走向“替代人”。四个范式不是互相替代，而是逐层叠加——下层提供数据与动作，上层提供自治与边界。

![四级台阶与回环：数字侧起步，物理侧闭环](/images/public/manthinking-career/ops-paradigm.jpg)

运维范式的定义与实现：

AIOps（数据智能）：以指标、日志、调用链为输入，靠模型完成异常检测、根因定位、容量与趋势预测。只负责“判断”不负责“动手”，结论交给人，落地形态是告警收敛、看板、排障建议。
差异点：有结论，无动作。

Agent Ops（单点执行）：把运维动作封装成工具（命令行、脚本、API、MCP Server），由单个智能体按 SOP 调用，执行前由人确认。解决的是重复操作的“最后一公里”，如重启、扩缩容、配置下发。
差异点：有动作，但只走单步、单工具。
注：Agent Ops 另有“运维 Agent 自身”（上下文、工具权限、记忆、评测、成本、版本）的读法，属第 3 章 AI-Native Infrastructure 中 LLMOps / AgentOps 的范畴，本章不取此义。

Agentic Ops（流程自治）：多智能体按角色分工（诊断、变更、验证、复盘），通过 MCP 与 A2A 协作，把一串动作编排成完整流程；人从“逐步确认”退到“确认目标与边界”。解决的是跨系统、跨步骤的长链路运维，如故障自愈、发布回滚、巡检闭环。
差异点：有流程，但作用域仍是数字世界（API / MCP / 命令行）。

Embodied Ops（具身运维）：运维智能体不再只经 API / MCP 操作数字世界，而是通过部署在物理环境中的传感器获得基础设施的真实状态，经由执行器（机器人、智能 PDU、BMC 带外管理、机电控制接口）直接作用于物理世界，形成“感知—决策—执行—反馈”的闭环，并在人在回路的安全约束下完成自主运维。
差异点：有身体，第一次把“感知”与“控制”闭到物理侧。
边界：IT 运维语境下的物理世界指数据中心（供配电、制冷、机柜资产与线缆）、边缘站点、终端设备，以及 IT/OT 融合场景，不含业务侧的工业控制本体。

自主运维（Autonomous IT）：不是第五种范式，而是前四层的组织级结果——变更、容量、成本、安全、服务水平在同一目标函数下自运转，人的角色从操作者变为目标设定者与风险兜底者。

四层对比：

| 范式 | 输入 | 决策权 | 执行通道 | 作用域 | 人的角色 |
| --- | --- | --- | --- | --- | --- |
| AIOps | 指标、日志、调用链 | 模型给建议，人做决定 | 无，只输出结论 | 数字 | 决策者 |
| Agent Ops | 任务指令、工具清单 | 单智能体，逐步确认 | 工具、API、脚本 | 数字·单点 | 确认者 |
| Agentic Ops | 目标、策略、权限 | 多智能体，边界内自主 | MCP、A2A、工单 | 数字·全流程 | 目标设定者 |
| Embodied Ops | 传感器、数字遥测 | 智能体，安全约束内自主 | 执行器、机器人、带外管理 | 物理 + 数字 | 安全兜底者 |

判断自己在哪一层，只看三件事：智能体能不能动手（判断 → 执行）、能不能串流程（单步 → 全链路）、作用于哪一侧（数字 → 物理）。三者依次递进，就是 AIOps → Agent Ops → Agentic Ops → Embodied Ops。

节奏提醒：执行通道往往先于治理能力建成，存在能力倒挂。自主度必须与可回滚、可观测、可审计三条护栏同步推进，否则越往物理侧走，一次误操作的成本越高。

命名说明：范式名统一用 Embodied Ops（具身运维）；若需要平台/产品名，可用 AgenticEnv（智能体在物理环境中的运行时），避免与范式混用。

# 第 5 章：Enterprise Information Services

ITSM、ITOM、ESM、服务治理

四个词常被混用，其实各自回答不同的问题：

ITOM（IT Operations Management）：回答“东西好不好”。面向基础设施与技术对象，管监控、事件、可用性、容量、性能。看的是设备与系统。
ITSM（IT Service Management）：回答“服务好不好”。以 ITIL 实践集为骨架（事件、问题、变更、配置、服务请求），面向用户与 SLA。看的是服务，不是设备。
ESM（Enterprise Service Management）：回答“这套方法能扩多大”。把 ITSM 的工单与目录模型从 IT 推到 HR、财务、法务，一个门户、一套流程语言。
服务治理（Service Governance）：回答“谁负责、谁买单、冲突怎么裁”。多团队、多供应商下的 SLA 约定、权责边界、成本分摊与仲裁机制，本质是组织设计而不是系统。

区分要点：ITOM 看对象，ITSM 看服务，ESM 看覆盖范围，服务治理看权责关系。演进顺序也是这四步：设备 → 服务 → 全企业 → 跨组织契约。

与第 4 章的连接：这四套系统是智能体的事实底座。CMDB 提供拓扑与影响面，ITSM 提供变更语义与工单上下文，ITOM 提供状态与趋势。配置项（CI）数据不干净，智能体就只能做动作、做不了判断——运维智能体落地的第一道门槛不是模型能力，是 CMDB 的准确率。

# 第 6 章：Technology Economics & FinOps

TBM、FinOps、TCO、ROI、Unit Economics

五个概念各自回答一个不同的问题，混用会让决策失真：

| 概念 | 回答的问题 | 尺度与口径 |
| --- | --- | --- |
| TCO | 买不买 | 全生命周期成本：采购、部署、运维、人力、迁移、退出 |
| ROI | 值不值 | 收益与投入之比，难点在收益侧量化 |
| TBM | 算到谁头上 | 按业务服务维度归集与分摊的技术支出 |
| FinOps | 现在怎么调 | 用量与成本的实时闭环：Inform、Optimize、Operate |
| Unit Economics | 单位效率 | 每千次请求、每 GB·月、每百万 token 的成本 |

![成本与产出：技术经济性的两端](/images/public/manthinking-career/finops-economics.jpg)

运维 ROI 的失真点：收益大多体现在 MTTR 下降、变更失败率下降、可用性提升这类间接指标上，直接报“节省人力”通常高估。做 ROI 要把间接收益折算成可审计口径，否则预算评审时一定被追问。

AI 时代新增两个成本项：GPU 利用率进入 TCO 的主项，token 成本进入单位经济性。判断（非事实）：FinOps 的边界会从“云账单”扩到“算力与 token 账单”，因为这两项的增长速度已经超过传统云资源。

# 第 7 章：Data & Decision Intelligence

数据分析、预测、决策模型、数字孪生

四级台阶，每级回答的问题不同：

描述（发生了什么）：指标、日志、链路，解决“看见”。
诊断与预测（为什么、会怎样）：根因定位、容量与故障预测，解决“解释”。
决策（该怎么做）：在约束下选动作，解决“取舍”。
执行闭环（做了有没有效）：动作落地与效果回收，解决“验证”。

决策模型的选型看约束是否明确：约束明确（有硬边界、可枚举）用规则引擎或运筹优化，可解释、可审计；约束模糊（开放语义、多目标冲突）用学习型策略或 LLM Agent，适应性强但不可解释。真实系统是两者串联——LLM 负责理解与拆解，运筹与规则负责收敛与兜底。

数字孪生：物理实体的在线同步镜像加仿真能力。要区分仿真与孪生，仿真是离线的假设推演，孪生是在线同步的状态映射。孪生的价值不在“看得见”，而在“先在孪生体上试，再在物理世界执行”。这正是第 4 章 Embodied Ops 的安全前置条件：没有孪生、或至少没有可回滚的预演机制，物理侧的自主度不应放开。

# 第 8 章：Complex Systems & Business Applications

复杂系统、产业数字化、系统级优化

复杂系统的判据：非线性、涌现、路径依赖、局部最优不等于全局最优。运维里的具体表现：小改动引发级联故障（故障规模近似幂律分布）、告警风暴、容量与成本互为约束、变更的收益与风险不可分离。

系统级优化与局部优化的区别：单服务降本会推高整体风险，单点高可用会拉高整体成本。系统级优化要写成带约束的目标函数——在可用性、成本、变更速度、安全四个约束下求整体最优，而不是让每个子系统各自最优。

产业数字化三个阶段：上系统（工具替代手工）→ 改流程（系统反向定义流程）→ 改组织（权责与考核随系统重构）。多数企业停在第一阶段，却用第三阶段的预期做预算，这是数字化投入回报出现落差的主要来源。

落点：前七章都是组件级优化，第八章是约束级优化。技术价值最终不由技术指标定义，而由业务约束定义——这是全篇的结论。
